# Scoping: unblocking the `physics_basics` example on the web path

Date: 2026-08-19
Branch: `asb/dart-physics-sample-clean` (PR #239, commit `470e44c9` — read via `refs/pull/239/head`)
Status: research only — no code changed.

## Background

PR #239 adds `examples/dart/examples_lib/lib/src/physics_basics.dart` (boxes and
spheres dropped onto a ground plane, simulated with `reactphysics3d_dart`,
rendered with `thermion_dart`). The example is registered in `registry.dart`
(headless CLI runner) but deliberately NOT in `galleryScenes` (web gallery),
because the web path is blocked. The original ticket (`.tickets/the-tvf4.md` in
the PR) required browser/WASM support as an acceptance criterion; it was
descoped for the reasons below.

Three blockers were claimed in the example's doc comment:

1. `reactphysics3d_dart` pins `ffigen_js 0.0.5-pre`; `thermion_dart` needs
   `^0.0.14-pre`; they only resolve via `dependency_overrides` in the example
   pubspecs.
2. Both packages' generated web bindings assign a single shared
   `NativeLibrary.instance` inside `initBindings`, so loading a second WASM
   module clobbers the first.
3. The `reactphysics3d_dart` WASM runtime path is unverified.

This document verifies each claim against the actual sources, then evaluates
options and recommends a path. Reference checkouts used (cloned at their
remote HEADs, plus the exact ref the PR pins):

- `reactphysics3d_dart` @ `52eec72e06b322080d395415bc1dfaffd8c45d2f` — this IS
  the current `master` HEAD; the PR pins it directly.
- `ffigen_js` @ `06d47ad` (master, `0.0.14-pre`).

## 1. Exact version state

| Package | ffigen_js constraint | File |
|---|---|---|
| thermion_dart | `^0.0.14-pre` | `thermion_dart/pubspec.yaml:24` |
| reactphysics3d_dart | `0.0.5-pre` (exact pin, no caret) | `pubspec.yaml` (dependencies) |

- ffigen_js master is `0.0.14-pre`. There are **no git tags**; versions are
  pubspec-only bumps. Version→commit map (from history): `0.0.5-pre` =
  `901616e`, `0.0.13-pre` = `65324d3`, `0.0.14-pre` = `06d47ad`.
- `reactphysics3d_dart` has no newer branch/tag relaxing the pin (branches:
  `feat/trigger`, `fix/linux-arm64-artifact`; neither touches `ffigen_js`).
- **The pin is a real dependency, not conservatism.** The checked-in generated
  web bindings `lib/src/bindings/src/rp3d_js_interop.g.dart` (3153 lines,
  header says "Generated by `package:jsgen`", the ffigen_js predecessor name)
  were produced by the 0.0.5-era generator and are **runtime-incompatible**
  with the 0.0.14 runtime, not merely version-locked:
  - Struct field access in the 0.0.5-generated code uses byte-offset pointer
    arithmetic, e.g. (from `RP3D_Vector3`):
    ```dart
    set x(double val) {
      NativeLibrary.instance.setValue(this.address + 4, val.toJS, 'float');
    }
    ```
    In 0.0.5, `Pointer.operator +` meant *byte offset*. In 0.0.14
    (`ffigen_js/lib/src/types.dart:39`) it means *element count*:
    `Pointer<T>(addr + numElements * sizeOf<T>())` — and
    `sizeOf<RP3D_Vector3>()` **throws `UnsupportedError`** (`types.dart:26-35`
    only knows primitives). thermion's own regenerated bindings use the new
    pattern (`this.address.addr + 0`, constructing a new `Pointer` — e.g.
    `thermion_dart_js_interop.g.dart:8788`), which is why thermion needs
    `^0.0.14-pre`.
  - Between 0.0.5 and 0.0.14 the runtime also changed `NativeType` subtypes
    from extension types to abstract classes, added heap-tracking to
    `Pointer.free()`, and (0.0.13, then restored in 0.0.14) fixed typed-data
    `.address` handling. Generated code from 0.0.5 is not guaranteed to
    compile, and definitely not to run, against 0.0.14.
- Consequence for the PR's `dependency_overrides` (`ffigen_js: ^0.0.14-pre` in
  `examples_lib`, `headless_runner`, and `web_gallery` pubspecs): it is "safe"
  only because nothing *runs* rp3d code on web today. The web build still
  *compiles* `rp3d_js_interop.g.dart` (it is exported from
  `examples_lib.dart` → `physics_basics.dart` → `reactphysics3d_dart` →
  conditional export), but any struct field access would throw at runtime.
  The override hides the conflict; it does not resolve it.

## 2. The `NativeLibrary.instance` singleton

**It is one process-wide global. There is no per-module or per-binding
keying, and no multi-module support in any ffigen_js version.**

- `ffigen_js/lib/src/types.dart:319`: `late NativeLibrary _lib;` — a single
  package-level global.
- `extension type NativeLibrary` (`types.dart:455-522`) exposes
  `static NativeLibrary get instance => _lib;`,
  `static set instance(NativeLibrary lib) { _lib = lib; }`, and
  `static void initBindings(String moduleName)` which does
  `globalContext.getProperty(moduleName.toJS)` (a lookup of a global JS
  variable by name, e.g. `window.thermion_dart`) and assigns `_lib`.
- The generator template (`ffigen_js/lib/src/jsgen/code_generator/writer.dart`,
  the block emitting `extension type GeneratedBindings(NativeLibrary _)`)
  generates into every bindings file:
  ```dart
  static GeneratedBindings get instance => NativeLibrary.instance as GeneratedBindings;
  static void initBindings(String moduleName) { ... NativeLibrary.instance = lib as NativeLibrary; }
  ```
  and every generated wrapper calls
  `GeneratedBindings.instance._fn(...)` (`func.dart:303`). Both
  `thermion_dart/lib/src/bindings/src/thermion_dart_js_interop.g.dart:11-20`
  and `reactphysics3d_dart/lib/src/bindings/src/rp3d_js_interop.g.dart:11-20`
  carry exactly this pattern.
- Critically, **all** ffigen_js runtime helpers route through the same `_lib`:
  `stackAlloc`/`malloc`/`free`, `makeUint8List`/`makeFloat32List`/…,
  `String.toNativeUtf8()`, `getValue`/`setValue` (used by *every* generated
  struct getter/setter in both packages), `addFunction`/`removeFunction`, and
  `HEAPU8`/`HEAPF32` (used by `asTypedList`).
- So with two separately loaded Emscripten modules, the second `initBindings`
  call doesn't just "clobber a variable": the loser's subsequent
  `setValue`/`stackAlloc` calls execute against the **wrong module's heap**
  (addresses are plain ints), i.e. silent memory corruption, not a clean
  error. Hand-written code reads the same singleton too
  (`thermion_dart/lib/src/bindings/src/js_interop.dart:18`).

How the JS side loads a module today (thermion gallery):
`web_gallery/web/index.html:136-147` loads `thermion_dart.js`
(Emscripten glue, `-sEXPORT_NAME=thermion_dart -sMODULARIZE`), awaits it onto
`window.thermion_dart`, then boots the dart2wasm `main.wasm`;
`web_gallery/web/main.dart:56` calls `NativeLibrary.initBindings("thermion_dart")`.
Two modules *can* coexist as JS globals (different `EXPORT_NAME`s), and each
exports the runtime methods ffigen_js needs (both builds pass the same
`-sEXPORTED_RUNTIME_METHODS=getValue,setValue,UTF8ToString,stringToUTF8,writeArrayToMemory,lengthBytesUTF8,HEAPU8,stackSave,stackRestore`
and `-sEXPORTED_FUNCTIONS=_malloc,stackAlloc,_free`); the blocker is purely
the Dart-side singleton.

## 3. True state of the `reactphysics3d_dart` web path (worse than "unverified")

- Generated web bindings **exist** (`rp3d_js_interop.g.dart`, 0.0.5-era — a
  usable starting point for regeneration).
- **Nothing initializes them.** No call to `initBindings` anywhere in the
  package; no loader JS; no `<script>` wiring; no async init hook.
  `createReactPhysics3D()` (`lib/src/reactphysics3d.dart:155`) constructs
  `FFIReactPhysics3D()` → `FFIPhysicsCommon()` whose constructor synchronously
  calls `rp3d_physics_common_create()`. On web today that path would hit a
  `LateInitializationError` on `_lib` (thermion's gallery sets the singleton,
  but to the thermion module).
- `lib/src/bindings/src/bindings.dart` selects per platform:
  `export 'ffi.dart' if (dart.library.ffi) 'ffi.dart' if (dart.library.js_interop) 'rp3d_js_interop.g.dart';`
  — which is why the native/headless path works under the version override.
- **The standalone web build is broken/incomplete in the repo.**
  `native/web/CMakeLists.txt` does
  `add_executable(${MODULE_NAME} module_init.cpp)` but `module_init.cpp` is
  not checked in; it also expects a prebuilt `libreactphysics3d.a` at
  `native/web/lib/`, and `native/web/` contains only the two cmake files.
  The comment in `native/web/reactphysics3d_dart.cmake` says it all: this
  cmake is meant to be included by a *bigger* client build ("…linked into the
  mixworld client build") — it appends
  `reactphysics3d_dart_static`/`reactphysics3d` to `EXTERNAL_ALL_LIBRARIES`.
- No prebuilt rp3d WASM is published anywhere (no download tool, no R2
  artifact). `BUILDING.md` covers macOS/iOS/Android/Linux native only.

## 4. Thermion's existing escape hatch: `EXTERNAL_PROJECTS`

`thermion_dart/native/web/CMakeLists.txt` already has a mechanism for building
third-party code **into the single thermion WASM**:

- Lines 132-157: if `EXTERNAL_PROJECTS` is defined (a list of paths to
  `.cmake` files), each is `include()`d; the included file appends targets to
  `EXTERNAL_ALL_LIBRARIES`.
- Lines ~340-371: `EXTERNAL_ALL_LIBRARIES` are linked into the one
  `thermion_dart` executable with
  `-Wl,--whole-archive` per library — explicitly "because nothing in Thermion
  directly references these libraries", i.e. exactly the situation for rp3d,
  whose `_rp3d_*` symbols are only referenced from Dart via JS interop.
- Both C API layers use `extern "C" + EMSCRIPTEN_KEEPALIVE`
  (thermion's `T*.cpp`; rp3d's `rp3d_c_api.cpp`), so rp3d's functions would
  appear on the combined `Module` object exactly like `_Thermion_*` do.
- This mechanism is what the downstream "mixworld" app uses today to combine
  thermion + reactphysics3d in one WASM (per the rp3d cmake comment and the
  PR ticket's reference app). It is **not** wired into thermion's own
  `make wasm` / CI (`scripts/`, `.github/` have no `EXTERNAL_PROJECTS`
  references).

Why one combined WASM dissolves the singleton conflict: there is only one
module, so thermion's `NativeLibrary.initBindings("thermion_dart")` (already
called at `web_gallery/web/main.dart:56` before any scene setup) sets the one
singleton to the combined module, which exports both `_Thermion_*` and
`_rp3d_*`. rp3d's `GeneratedBindings.instance` reads the same singleton and
resolves correctly. **No ffigen_js change and no second initBindings call are
needed.** The second requirement is free: `FFIPhysicsCommon`'s synchronous
constructor runs after the gallery's initBindings.

## 5. Options

### Option A — relax the pin + regenerate rp3d's web bindings
**Repo: reactphysics3d_dart only.**

- Bump `ffigen_js` to `^0.0.14-pre`, run
  `dart run ffigen_js --config ffigen/web.yaml` (config already exists and
  mirrors thermion's `ffigen/web.yaml`), fix any fallout in the hand-written
  `implementation/ffi_*.dart` files (they use wrapper functions and the
  `StructAllocator`/typedef shims from `bindings.dart`, so fallout should be
  small), keep native tests green.
- Does **not** by itself deliver web: still no module loading, and if two
  modules were loaded the singleton conflict would remain.
- **Effort: 0.5–1 day. Risk: low. This is a prerequisite for every web
  path**, and it also removes the need for the PR's three
  `dependency_overrides` entries.

### Option B — two separate WASM modules on one page
**Repos: ffigen_js + reactphysics3d_dart + thermion_dart.**

- Requires a real ffigen_js redesign: per-binding library instances instead of
  one `_lib`. The hard part is not the generated wrappers (each
  `GeneratedBindings` could hold its own static) but the **shared helpers** in
  `types.dart` (`stackAlloc`, `toNativeUtf8`, `makeFloat32List`,
  `getValue/setValue`, `HEAPU8`-backed `asTypedList`) that both packages'
  generated code calls — they must dispatch on the *caller's* module, which
  means passing the library through every generated call or a zone-based
  "current library" (fragile). Then: regenerate both packages' bindings,
  update hand-written uses (`thermion_dart/.../js_interop.dart`),
  build+publish a second Emscripten artifact for rp3d (its standalone web
  build needs `module_init.cpp` restored), extend the gallery `index.html` to
  load and await both modules, and add a second `initBindings` call.
- Also doubles committed memory (both builds use `-sINITIAL_MEMORY=512mb
  -sALLOW_MEMORY_GROWTH=0`) and adds a second pthread pool.
- **Effort: 1.5–3 weeks** (ffigen_js API redesign + three coordinated
  releases + new artifact pipeline). **Risk: high.** Worst
  payoff-for-effort; only worth it if two *independent* WASM modules ever
  need to coexist generally.

### Option C — one combined WASM via `EXTERNAL_PROJECTS` (recommended)
**Repos: reactphysics3d_dart (Option A) + thermion (build wiring) + tiny examples change.**

1. reactphysics3d_dart: Option A (pin bump + regenerate).
2. thermion: wire `EXTERNAL_PROJECTS` into the web WASM build —
   `make wasm` / web CI clones reactphysics3d_dart at a pinned ref (or fetches
   a published emscripten build of `libreactphysics3d.a`; rp3d vendors the
   engine source at `native/include/reactphysics3d/`, so
   `emcmake`-building it in CI is straightforward), passes
   `-DEXTERNAL_PROJECTS=<...>/native/web/reactphysics3d_dart.cmake`, uploads
   the new zip, bumps `web.version`. Whole-archive linking keeps `_rp3d_*`
   alive; thermion's Dart code needs **zero changes**.
3. thermion examples: delete the `dependency_overrides` blocks from the three
   pubspecs, add a `'physics': setupPhysicsBasics` entry to `galleryScenes`
   (`examples/dart/examples_lib/lib/src/registry.dart`), verify in a browser
   (the gallery's headless Chrome check can cover it).
- **Effort: ~2.5–4 days total** (A: 0.5–1d; build/CI wiring: 1–2d; gallery +
  cleanup: 0.5d). **Risk: medium-low.** Precedent: the mechanism exists and is
  exercised downstream by mixworld today.
- Tradeoff: the *shipped* `thermion_dart.wasm` now carries rp3d —
  likely +1–2 MB and a version coupling (thermion `web.version` bumps must
  track the rp3d ref). Given the project already ships a ~512 MB-initial-memory
  Filament build and previously considered building libassimp into the same
  artifact, this coupling is consistent with how the project treats the web
  artifact.

### Option D — keep physics out of the gallery; dedicated web page
- A dedicated example page with its own build either (a) still loads two
  modules → blocked exactly like Option B, or (b) builds a one-off combined
  WASM → all of Option C's build plumbing *minus* the shipped-artifact update,
  but with a second artifact pipeline to maintain and no gallery visibility.
  Only sensible if the owner refuses to ship rp3d inside the main artifact.

### Option E — other ideas considered and rejected
- **Compile both into one WASM at the Dart level** — not applicable; the
  split is at the C/Emscripten level, not Dart.
- **Per-package renamed copies of the ffigen_js runtime** (two package names,
  two `_lib`s) — works in principle, needs no ffigen_js upstream change, but
  requires maintaining a fork/rename and regenerating rp3d against it; more
  moving parts than Option C with no benefit.
- **Status quo** (PR as-is: native/headless only) — zero cost, web stays
  blocked, `dependency_overrides` keep papering over the conflict.

## 6. Recommendation

**Option C, in this order:**

1. **reactphysics3d_dart** — relax `ffigen_js` to `^0.0.14-pre`, regenerate
   `rp3d_js_interop.g.dart`, add a CI step that analyzes/builds the web
   bindings (nothing currently verifies them). *(0.5–1 day)*
2. **thermion** — wire `EXTERNAL_PROJECTS` into the web WASM build + CI,
   publish a new `thermion_dart-<version>-web.zip`, bump `web.version`.
   *(1–2 days)*
3. **thermion examples** — drop the three `dependency_overrides` blocks, add
   the scene to `galleryScenes`, verify. *(0.5 day)*
4. **ffigen_js (optional hardening, not required)** — make
   `NativeLibrary.initBindings` warn when re-pointing at a different module,
   and document the one-module-per-page limitation. *(0.5 day)*

**What must change where:**

| Repo | Required change |
|---|---|
| reactphysics3d_dart | pubspec pin bump; regenerate web bindings with ffigen_js 0.0.14; (ideally) CI coverage for the web bindings |
| thermion | web WASM build/CI: link rp3d via `EXTERNAL_PROJECTS`; new artifact + `web.version` bump |
| thermion examples | remove `dependency_overrides`; add `physics` to `galleryScenes` |
| ffigen_js | nothing required (optional: initBindings guard + docs) |

**Upstream ffigen_js work: none under Option C.** General multi-module support
(Option B) is a separate, larger project that should only be started if two
independent WASM modules ever need to coexist on one page.
